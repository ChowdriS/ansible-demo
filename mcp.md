# MCP Session Gateway — what I built and tried

A working proof-of-concept for the problem in
`dynamic-mcp-session-scoping-research.md`: one real MCP server, many
concurrent callers, each one only seeing/using a subset of its tools chosen
per-task. This doc explains what exists right now, plainly, so it can be
corrected before going further.

## The problem, in one sentence

A customer has one real MCP server with a big tool catalog (in my test,
GitLab's MCP server, 64 tools after filtering). Different agents/tasks
should only see the handful of tools relevant to what they're doing, and
this has to work correctly even when many such sessions are hitting the
same backend at the same time.

## What I actually built

A small gateway that sits in front of the real MCP server:

```
customer's real MCP server (e.g. GitLab MCP, 64 tools)
              ^
              | (gateway holds the only real connection to it)
              |
   ┌──────────────────────┐
   │   the gateway         │
   │  (this project)        │
   └──────────────────────┘
        ^              ^
        |              |
   Session A       Session B
  (5 tools, CI/CD)  (4 tools, merge requests)
```

**Two-step flow:**
1. `POST /register` — give the gateway the real backend's URL, once. Get
   back a `backend_id`.
2. `POST /sessions` — give it a `backend_id` + a plain-English task
   description ("check CI/CD pipeline status and job logs"). It fetches the
   backend's full tool catalog, asks Claude to pick the relevant subset, and
   hands back a signed token that only grants those tools.

Whoever/whatever is going to actually use the tools then connects an MCP
client to the gateway's `/mcp` endpoint, sending that token as
`Authorization: Bearer <token>` on every request. From that point on, that
session's `list_tools()` only shows its own subset, and calling anything
outside that subset gets rejected before the real backend is ever touched.

## Files

```
gateway/
  registry.py        -- remembers registered backends (url -> id), in-memory
  session_token.py    -- mints/verifies the signed scope token (see below)
  tool_selector.py    -- asks Claude to pick a tool subset for a task; falls
                          back to plain keyword matching if no model is configured
  upstream.py          -- talks to the real backend MCP server
  mcp_gateway.py        -- the actual per-session filtering logic (the core piece)
  main.py                -- the FastAPI app: /register, /sessions, mounts /mcp
demo/
  run_demo.py            -- runs the whole thing end to end against a real backend
```

## The token — what it is and why

Each session gets a signed token (JWT, HMAC-SHA256) containing: which
backend it's for, exactly which tool names it's allowed to call, and an
expiry time. It's sent as an HTTP header (`Authorization: Bearer ...`), never
in a URL.

Why this shape, specifically, tying back to the research doc's list of
"just create a key" problems:
- **Tamper-evidence**: the signature covers the tool list itself. Editing
  the allowed tools in the token invalidates it.
- **Not a guessable/enumerable ID**: it's a signed token, not a sequential
  or predictable key.
- **Not in a URL**: avoids the URL-logging/leakage problem the research doc
  flags — it only ever travels in a header.
- **Revocation**: added a small in-memory "revoked" list, checked at verify
  time, so one session can be killed without touching any other (tested,
  works — see below).

What it does **not** do: full OAuth/RFC 8693 token exchange (the research
doc's "most production-grade" option). This is a simpler, self-contained
version of the same idea, not the whole thing.

## How the per-session filtering actually works

This was the main technical unknown going in: does the MCP Python SDK let a
server return a *different* tool list depending on who's asking?

Answer: yes, but not through a documented "session" feature — through
reading the raw request. The SDK gives request handlers access to the
current HTTP request (headers and all) via a context object. So the
gateway's `list_tools` and `call_tool` handlers both: read the
`Authorization` header off the actual incoming request, verify+decode the
token, and only then decide what to show/allow. Every request is checked
fresh — nothing is decided once and cached per "session" in the MCP
protocol's own sense.

Important distinction I want to flag clearly: MCP's own `Mcp-Session-Id`
(auto-generated by the SDK, one per client connection) is **not** used for
authorization here at all — it's just internal connection bookkeeping. All
the actual scoping logic runs off the token in the header, independent of
that ID. I made this choice because the MCP session ID isn't something the
client gets to choose ahead of time (the server assigns it), so it can't
carry meaning the way the research doc wanted `agentrelay.com/mcp/gh/1` to.
Open to being told this should work differently.

## What I actually tested, with real output

Ran the whole thing against the real GitLab MCP server used elsewhere in
this project (64 tools). `demo/run_demo.py` does this automatically:

```
1. Register the real backend                    -> backend_id, 64 tools seen
2. Mint two sessions, different task descriptions:
     Session A ("check CI/CD pipelines")  -> 5 tools (list_pipelines, get_pipeline, ...)
     Session B ("review merge requests")   -> 4 tools (list_merge_requests, get_merge_request, ...)
     (zero overlap between the two, both picked by Claude, not hardcoded)
3. Both sessions call list_tools() at the same time (asyncio.gather)
     -> each one only sees its own subset. No cross-talk.
4. Session A calls one of its own tools       -> allowed (failed on a missing
                                                   argument, which is a
                                                   separate, expected thing —
                                                   the scope check itself passed)
5. Session A calls a Session-B-only tool       -> DENIED, with the real
                                                   backend never contacted
6. Revoke Session A, try again                  -> DENIED, even though the
                                                   token hadn't expired yet
7. Session B, untouched by A's revocation        -> still works fine
```

All seven of those actually ran and produced that output — this isn't a
plan, it's what happened.

## Things worth flagging honestly before going further

- **One real bug I want to call out in the SDK's behavior, not mine**: when
  a tool call is denied, the MCP client library does **not** raise an
  exception — it returns a normal-looking result with `isError=True` inside
  it. My first version of the demo assumed a denial would raise, and it
  silently reported false passes until I caught this and fixed the demo's
  own checking logic. Anyone else building against this needs to check
  `result.isError`, not wrap calls in try/except and assume errors raise.
- **The upstream connection is opened fresh per call**, not pooled/reused.
  Simple and correct, but not efficient — fine for a demo, would need
  pooling for real traffic.
- **Registry and revocation list are both in-memory**, wiped on restart. No
  persistence yet.
- **Tool selection quality** is whatever Claude decides from tool
  name+description alone — no evaluation of how good/complete the picks
  are, just that the mechanism (different sessions get different,
  enforced subsets) works.
- I used one internal/private attribute of the `mcp` SDK
  (`FastMCP._mcp_server`) to register the per-request handlers, because the
  public `FastMCP.list_tools()`/`call_tool()` methods turned out to just be
  plain getters, not the registration hooks I expected. Flagging this
  because a leading-underscore attribute isn't a guaranteed-stable API —
  worth knowing if the `mcp` package version changes later.
- Nothing here touches AWS AgentCore/microVM isolation (the third question
  in the research doc) — this is purely the MCP-gateway layer, run locally.

## How to run it yourself

```bash
cd hack/mcp-session-gateway
pip install -r requirements.txt
export GATEWAY_SECRET_KEY=$(python3 -c "import secrets; print(secrets.token_hex(32))")
# optional, for real LLM-based tool selection instead of keyword fallback:
export CLIPROXY_BASE_URL=...
export CLIPROXY_API_KEY=...
python -m demo.run_demo
```
